# Стенд бизнес-бенчмарков Гипер Базы

Методика — [../BENCHMARK_PLAN.md](../BENCHMARK_PLAN.md). Здесь — как повторить прогон.

## Состав

| Файл | Что делает | Где выполняется |
|---|---|---|
| `run.sh` | оркестратор: готовит узел, гоняет сценарии, собирает метрики, возвращает всё назад | локальная машина |
| `bench.node.ts` | генератор нагрузки: пишет с заданным темпом, читает, считает перцентили | локальная машина, собирается в `-/node.js` |
| `summary.sh` | сводит папку прогона в одну таблицу: задержки против цены для узла | локальная машина |
| `results/` | по папке на прогон: сырые замеры, метрики узла, manifest | локально |
| `state/` | что скрипт изменил на узле, чтобы `restore` знал, что откатывать | локально |

## Роли машин

- **Генератор** — эта локальная машина. Здесь крутится `bench.node.ts` и отсюда идёт ssh на узел.
- **Узел под тестом (SUT)** — `91.188.212.151`, 4 vCPU / 8 GB. Первый этап меряем только его.
- **Второй узел** — `87.120.36.150`, 1 vCPU / 960 MB. Подключается на втором этапе, для проверки масштабирования.

Генератор и узел обязаны быть разными машинами: сборка пакета на клиенте примерно впятеро дороже его приёма на сервере, и на одной машине они дерутся за ядра.

## Порядок прогона

```bash
cd giper/bench

./run.sh prep          # остановить лишнее, поднять чистую базу, отвязать от чужого мастера, открыть порт
./run.sh baseline 600  # 10 минут фонового шума простаивающего узла — нужен для сравнения
./run.sh s2            # потолок приёма
./run.sh s3            # веер
./run.sh s4            # офис, много лендов
./run.sh restore       # вернуть узел как было
```

`prep` спрашивает подтверждение перед остановкой чужих контейнеров и перед подменой тома. Для неинтерактивного запуска — `FORCE=1 ./run.sh prep`.

`restore` обязателен: он поднимает обратно остановленные контейнеры, снимает правило iptables и закрывает порт в ufw. Если прогон прервался — просто запусти его отдельно.

## Что `prep` меняет на узле

Всё обратимо и всё откатывается в `restore`:

1. **Останавливает посторонние контейнеры** — `gram-push`, `deploy-back-1` (ragu-api), `figmol-oauth`, `bzrl-parser-bot`, `run-watchtower-1`. Список сохраняется в `state/containers_stopped.txt`. `run-caddy-1` намеренно оставлен: он терминирует TLS для домена базы, а при простое ничего не ест.
2. **Останавливает watchtower** — иначе он обновит образ посреди прогона и обесценит результат.
3. **Отвязывает от публичного мастера** — `iptables -I OUTPUT -d 91.219.148.98 -j REJECT`. Адрес вшит в бандл через Seed, поэтому проще закрыть маршрут, чем пересобирать. На втором этапе это правило снимается и вместо него собирается свой Seed на два узла.
4. **Открывает порт 9090** в ufw для внешнего IP генератора (определяется автоматически). По умолчанию ufw пускает только 22, 80, 443, 8443, 8444.
5. **Отводит непустой том** базы под именем `run_baza_public_pre_bench_<дата>`, чтобы прогон стартовал с чистых данных. Обратно скрипт его не возвращает — это делается руками осознанно.

## Что проверяет `check`

Запускается автоматически в конце `prep`, но полезен и сам по себе:

- база запущена, счётчик перезапусков виден;
- **нет флага `giper_baza_log`** — при нём в `stat.tick()` срабатывает ранний выход «Stat disabled due logging» и встроенная статистика не собирается вовсе;
- в свежих логах нет обращений к внешним мастерам;
- порт доступен с генератора;
- load average узла перед стартом.

## Ключ прогона

Генератор на старте создаёт свежий ключ (`$giper_baza_auth.grab()`, это Proof of Work, занимает секунды) и раздаёт его всем изолятам прогона: писателю и читателям. Одна личность — один Home Land, поэтому читателям не нужно передавать ссылку на ленд.

Хардкодить ключ, как делает старый бенчмарк в `giper/baza/bench/bench.ts`, больше нельзя: формат вырос до 128 байт, `$giper_baza_auth.current()` явно это проверяет, а на коротком ключе подпись юнитов падает с `RangeError: Invalid typed array length` в `asArrayPrivate()`. **Старый бенчмарк по этой причине сейчас не работает вовсе** — он молча доходит до стадии Making и завершается. Если понадобится повторить прогон в том же ленде, ключ передаётся аргументом `auth=<строка>`.

## Метрики узла

На узле нет ни `sysstat`, ни `jq`, и ставить их не нужно — мы меряем узел, а не менять его. Сборщик читает `/proc` напрямую и пишет CSV раз в секунду:

`ts, cpu_user_s, cpu_sys_s, rss_mb, threads, sock_est, disk_read_mb, disk_write_mb, load1, mem_free_mb`

`cpu_*` — накопительные секунды процессорного времени процесса базы, разность между соседними строками даёт загрузку ядра. `disk_*` — накопительные мегабайты по диску целиком; разность за прогон, делённая на число полезных дельт, и есть write amplification.

Встроенная статистика базы (`$giper_baza_app_stat`: Land active, Port slaves, Errors) снимается отдельно во вкладке Stat — в CSV она пока не выгружается.

## Формат результата

```
results/20260812-1430-s2-ingest/
├── manifest.txt          на чём мерялось: образ, коммит baza, ядра, что ещё крутилось
├── rate-25.log           вывод генератора: sent, received, p50, p95, p99, max
├── rate-25.ndjson        сырьё: строка на операцию, {t, land, lat}
├── rate-25.metrics.csv   метрики узла посекундно
└── …
```

`manifest.txt` пишется автоматически и включает хэш коммита `giper/baza` и признак незакоммиченных правок. Без него через неделю невозможно понять, к какой версии относятся цифры.

Свести прогон в таблицу:

```bash
./summary.sh results/20260812-1754-s2-ingest
```

```
point              sent     recv    p50    p95    p99    max    cpu%    rss    wrMB
warmup             1500     1495      6      9     13     18    14.1    252    25.7
```

`recv` меньше `sent` — это не обязательно потери: читатель опрашивает значение раз в миллисекунду и несколько быстрых перезаписей подряд видит как одну. Разрыв закономерно растёт с темпом. Настоящие потери отличаются тем, что растут и при неизменном темпе.

`wrMB` — записанное на диск узла за точку, по всему диску. На пустом узле фон нулевой, так что это запись базы: делённая на число дельт (по 184 байта), она и даёт write amplification.

## Второй этап: связать узлы

После того как одиночный узел измерен:

1. Снять правило iptables (`restore` это делает).
2. Собрать свой Seed на два пира — так узлы увидят друг друга и не увидят никого больше. Либо, как быстрый вариант, прописать одному узлу `masters_default` со ссылкой на второй.
3. Достаточно, чтобы **одна** сторона знала адрес другой: канал двусторонний, `ports() = masters + slaves`, и `sync_port_lands` льёт по всем портам одинаково.
4. Гонять S10–S12 из плана: задержка репликации, разрыв и догон, слабый узел.
